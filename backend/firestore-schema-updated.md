# Firestore Schema Reference — Spiritual Vastu Bhandar (version 1)

Database: Cloud Firestore Standard, region `asia-south1`. Backend: Python Cloud Functions. Auth: Firebase Authentication (Google, Email/Password).

This is the agreed version 1 schema and implementation reference. Business decisions explicitly deferred to later phases are listed near the end.

## Conventions

- **Money:** integer paise (₹299 = `29900`). Never floats.
- **Timestamps:** Firestore timestamps, set by the server (server timestamp or Cloud Function), not by the browser.
- **Variant IDs:** stable, never reused, never derived from labels. Use only `a-z`, `0-9`, `_` (no dots, spaces or slashes, because dots break field-path updates). Products without options use one variant, `default`.
- **Images:** store Firebase Storage **paths**, not URLs. Use `products/{productId}/{filename}` and `categories/{categoryId}/{filename}`. The frontend builds download URLs using the bucket name from an environment variable.
- **No hard deletes** of ordered products or variants. Set `isActive: false`.
- **Query filters that the rules require:** categories and products must be queried with `isActive == true`; customer orders with `userId == <own uid>`. Rules do not filter results.
- **Admin:** custom claim `admin: true` (and a verified email). No role field in Firestore.

**`items[]`:** `productId`, `variantId`, `productName`, `variantLabel`, `sku`, `imagePath` (where available), `unitPrice`, `quantity`, `lineTotal`, `weightGrams` (if needed).

**`totals`:** `subtotal`, `shipping`, `codFee`, `discount` (if introduced), `total`. All integer paise, calculated by the backend, never taken from the frontend. Structure stays flexible until shipping and COD policies are decided.

**`payment`:** `status`, `amount`, Paytm order and transaction references, verification timestamps. No credentials or secrets.
- `status` values: COD `pending` (to be collected) then `collected`; Paytm `pending`, `paid`, `failed`, `uncertain`.
- COD collection is recorded by a protected function, including `collectedAt` and the actor who recorded it.
- `needsReview` (boolean): set when money may have been deducted despite a failure or a late payment cannot safely be fulfilled. The admin dashboard must be able to list these orders even if email delivery fails.

Payment status is kept separate from order status.

### Order statuses

`pending_payment`, `confirmed`, `shipped`, `delivered`, `payment_failed`, `expired`, `cancelled` (reserved for future manual cancellation). COD orders start at `confirmed`.

Allowed transitions (enforced by protected backend functions; never by direct client or admin Firestore writes):

| From | To | Who |
|---|---|---|
| `pending_payment` | `confirmed` | Payment verification function |
| `pending_payment` | `payment_failed` | Payment verification function (confirmed failure only) |
| `pending_payment` | `expired` | Scheduled expiry job (after status check with Paytm) |
| `confirmed` | `shipped` | Admin, via function |
| `shipped` | `delivered` | Admin, via function |
| `confirmed` | `cancelled` | Admin, via function (future; restores stock once) |

`delivered`, `payment_failed`, `expired`, `cancelled` are terminal. Cancelling a delivered order is not allowed by default. Cancelling a shipped order is undecided.

## Inventory

- Stock lives at `products/{productId}.variants.{variantId}.stock`.
- The order function checks current price and stock and decrements stock **in one Firestore transaction**.
- COD: stock deducted when the order is accepted. Paytm: stock reserved when payment begins; the reservation expires after about 15 minutes.
- Confirmed Paytm failure or expiry: release stock **exactly once**. If the payment status is uncertain, verify with Paytm before releasing.
- Payment calls and emails never run inside a Firestore transaction (transactions can retry).
- Admin stock edits must not overwrite concurrent order changes. Stock set/adjust goes through a transactional backend function; other catalog fields can be edited directly with field-level updates.
- One shared, idempotent stock-restoration routine serves failed payments, expiry and future cancellation.
- Low stock: `0 < stock <= threshold`; out of stock: `stock == 0`. Default threshold is 5, kept in one shared admin-app config constant for version 1; do not create a separate configuration collection.
- The dashboard shows product name, variant label and exact quantity.
- A stock-movement audit collection is deferred.

**Scalability note:** embedded variants cannot be queried by stock across products. The low-stock view reads the product documents and checks variants in the browser. That is one read per product per load (about 120 reads for this catalog), which is fine. If the catalog grows large, add a derived field on the product document (not a new collection), maintained by the stock function, such as the lowest active-variant stock, and query on that.

## Payment failure handling

- Paytm confirms failure: order `payment_failed`, stock released once.
- Money may have been deducted despite failure: email the client for manual investigation and refund; set `payment.needsReview`. No automatic refunds.
- Uncertain result: verify the final status first. Do not release stock or fail the order before then.
- If Paytm reports success after the reservation has expired, verify the payment and attempt to reserve the required stock again transactionally. If stock is unavailable, do not fulfil the order normally; keep it `expired`, set `payment.needsReview`, and notify the client for manual investigation/refund. No automatic refund.
- Email delivery, retries and duplicate prevention are deferred to the email phase. COD emails must show the backend-calculated amount to collect.

## Queries and indexes (composite)

| Collection | Index fields | Used by |
|---|---|---|
| `categories` | `isActive` ASC, `sortOrder` ASC | Active categories, ordered |
| `products` | `isActive` ASC, `sortOrder` ASC | All active products, ordered |
| `products` | `isActive` ASC, `categoryId` ASC, `sortOrder` ASC | Active products in a category |
| `orders` | `userId` ASC, `createdAt` DESC | Customer order history |
| `orders` | `status` ASC, `createdAt` DESC | Admin filter by status |
| `orders` | `status` ASC, `reservedUntil` ASC | Expiry job: `pending_payment` and `reservedUntil` in the past |

Single-field queries (all orders by `createdAt`, admin product list) need no composite index. These indexes go in `firestore.indexes.json`. The emulator may not enforce missing indexes, but the deployed database does.

## Agreed implementation requirements

1. Paytm orders use `reservedUntil`; any stock restoration records `stockReleasedAt` in the same transaction so stock is restored at most once.
2. Payment status is separate from order status. COD collection is recorded through a protected function with timestamp and actor. `payment.needsReview` identifies payments requiring manual investigation.
3. Order status transitions are enforced by protected backend functions. Customers and admins cannot directly write order status, totals, payment state, or stock-reservation fields in Firestore.
4. A late Paytm success is verified. The backend attempts to re-reserve stock; if unavailable, the order remains `expired`, is marked `needsReview`, and the client is notified for manual investigation/refund.
5. Stock set/adjust operations use a transactional backend function. Catalog edits must not overwrite stock fields.
6. `orderNumber` is generated uniquely by trusted backend logic. Slugs and SKUs must be unique when supplied; check in the admin workflow and enforce in trusted backend logic where concurrent writes are possible. Validate Paytm order-ID format during payment integration.
7. Checkout requires a verified email. Support Google and Email/Password authentication; the customer profile's email is copied from Firebase Auth, and order email snapshots use the verified Auth identity.
8. Storage rules support both `products/{productId}/{filename}` and `categories/{categoryId}/{filename}` image paths, with public read access only where intended and admin-only writes subject to file type and size limits.
9. Customers can read only active categories/products and their own orders. Firestore rules do not filter query results, so client queries must include the required filters.
10. The first admin is bootstrapped using a trusted local Admin SDK script after confirming the correct Firebase project and account. Admin privileges use the Firebase Auth custom claim `admin: true` plus a verified email; never a client-editable Firestore role field.

## Deferred business decisions

- Shipping charges, COD fee, minimum and maximum order values, pincode restrictions, quantity limits, and any tax/GST rules.
- Email provider, delivery implementation, retries, and duplicate prevention (handled in the later email phase). Customer and client order emails must use backend-calculated totals; COD emails must clearly state the amount to collect.
- Cancellation workflow implementation (deferred): customer contacts the admin and provides the Order ID; the admin checks the request and manually changes the status through a protected function. No customer self-service cancellation or automatic refund. If cancellation is approved, restore stock exactly once. Paytm refunds are handled manually by the client. Define any additional cancellation fields when implementing this phase.
- Stock-movement audit collection.
